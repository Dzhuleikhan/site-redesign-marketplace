# Конвейер «сначала Figma, потом код»

После выбора концепта работа идёт в два этапа. Шаг `redesign-figma`: весь дизайн (главная,
каждая страница, модалка и состояние, в темах, которые выбрал пользователь, 1440 и 375) собирается в Figma
по концепту и проходит ревью. Шаг `redesign-code`: код пишется ТОЛЬКО по утверждённым фреймам.
Писать код страницы, у которой нет утверждённого фрейма, запрещено — главной тоже.

Основной исполнитель — менеджер проекта: он держит очередь, раздаёт пакеты агентам, читает
их отчёты и сам ничего не рисует и не верстает.

## Подготовка (менеджер)

1. Спросить ссылку на Figma-файл. Создать в нём НОВУЮ страницу рядом с существующими
   (например, «Redesign <год> (Claude)»). Чужие страницы файла не трогать никогда.
2. Создать рабочую папку конвейера (вне репозитория) с тремя файлами:
   - `BRIEF.md` — общий бриф для всех агентов: выбранные темы, файл и id страницы Figma, адрес dev-сервера,
     путь к репозиторию, правила режима экономии (ниже), планка качества, разрешения на ночь;
   - `DECISIONS.md` — обязательные решения (канон главной, что убрано, что скрыто, источник
     истины для каждого блока);
   - `inventory.md` — опись: маршруты, секции, модалки, состояния; у каждого статус
     НОВОЕ / СМЕШАННОЕ / СТАРОЕ.
3. Сверить опись с макетами главной и вывести пакеты работ (кит → хром → виджеты каталога →
   страницы по разделам → модалки → мобильные версии) с зависимостями.

## Источник истины

- Вид: артборды выбранного концепта, затем фреймы Figma. Текущий сайт — никогда не образец
  внешнего вида.
- Структура и тексты: живой сайт и код. Набор и порядок секций, данные, состояния, тексты
  берём оттуда; вид рисуем в каноне концепта.
- Закрытые страницы без тестового аккаунта собираются по коду: файлы маршрута, виджеты,
  тексты из английской локали.

## Порядок этапов

1. **Хром и кит** по концепту. Мастера шапки (гость и авторизованный), сайдбара, футера и
   набор общих элементов (кнопки, поля, табы, чипы, карточки, таблица, заголовок секции) —
   обе темы. Хром во всех фреймах — экземпляры этих мастеров.
2. **Главная** по артбордам концепта со всеми секциями из описи. Её блоки становятся
   мастерами для остальных страниц.
3. **Страницы** по разделам, затем **недостающие страницы и состояния** (детальные страницы,
   открытые панели, поиск, пустые состояния, закрытые разделы).
4. **Модалки** — единая оболочка по образцу модалки входа.
5. **Мобильные версии 375**.
6. **Ревью дизайна** отдельным агентом, который фреймы не рисовал: структура против описи,
   планка качества, поломки вёрстки (наложения, вылезающие элементы), обе темы.
   Поломки ищутся скриптом-аудитом по ВСЕМ узлам фрейма: элемент за краем страницы, колонка
   контента шире места справа от сайдбара, секция шире колонки, ребёнок за пределами карточки.
   Мелкий скриншот целого фрейма такие поломки не показывает — смотреть края крупно.
Точка утверждения: пользователь смотрит страницу Figma. Дальше — шаг `redesign-code`.

## Этап кода

7. **Код** по пакетам: тема и шрифты → кит → хром → главная → страницы → модалки. Агент
   читает фрейм через `get_design_context`, правит только свои файлы, после пакета
   прогоняет проверки репозитория (если пользователь разрешил).
8. **Ревью кода** против описи: каждый маршрут покрыт, от старого вида ничего не осталось,
   правила репозитория соблюдены.
9. **Браузерная сверка**: живой сайт против фрейма, 1440 и 375, обе темы.

## Режим экономии (обязателен)

Параллельные агенты сжигают лимит очень быстро. Поэтому:
- агенты по одному; второй параллельно только на маленькую точечную правку;
- агентам на механическую работу (перенос, замена клонов, сверка) — более дешёвая модель;
- каждый агент получает один пакет и читает только свои строки описи и решений (grep, а не
  файл целиком);
- агенты клонируют мастера, а не рисуют заново; строят крупными скриптами за один вызов;
- проверка — один скриншот фрейма в масштабе 0.4–0.5, без перепроверок вблизи;
- отчёт агента — не длиннее 15–20 строк, без таблиц со всеми id слоёв;
- замеры живого сайта — через JS (размеры, вычисленные стили, тексты), а не серией скриншотов;
- агента, который упёрся в бюджет, не пересоздавать, а продолжать сообщением: он сохраняет
  уже снятые данные.

## Планка качества (вписать в BRIEF)

Внутренние страницы должны быть такими же насыщенными, как главная. Промо- и инфоблоки
повторяют язык баннеров главной: панель со слэшами, арт целиком в кадре и на всю высоту,
цифры в цветных плашках, кнопки только из кита. Запрещено: белые коробки с пустотой, мелкие
или криво обрезанные арты, тени у заголовков, цвета и градиенты вне палитры, двойные рамки
и вылезающие из карточки элементы.

## Работа без пользователя (ночью)

- Перед уходом пользователя назвать, что может остановить работу: сон компьютера, закрытое
  приложение Claude, остановленный dev-сервер, окна разрешений, перезапуск сессии.
- Поставить себе отложенные проверки (`send_later`) каждые 1–1,5 часа: остановленного агента
  продолжить, закончившего — сменить следующим пакетом; утром — сводка.
- Спросить разовое разрешение на проверки репозитория (typecheck, lint, генерация ключей i18n)
  на эту ночь и записать его в BRIEF; git-записи по-прежнему запрещены.
- Честно назвать, что успеется к утру, а что нет.

## Ловушки Figma

- WebP, залитый сырыми байтами, принимается с успехом, но не отображается. Перед загрузкой
  конвертировать в PNG (иконки, маскоты) или JPEG (сцены).
- Серверный скриншот бывает закешированным — проверять `node.screenshot()` внутри скрипта.
- Файлы из `/tmp` не загружаются: копировать в рабочую папку.
- Встроенный браузер со скрытой панелью не догружает ленивые секции — для структуры читать код.
- Хром во фреймах держать экземплярами мастеров: правка мастера чинит все страницы сразу.
